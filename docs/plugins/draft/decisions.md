## Accepted user direction

The following records the meaning of the user's numbered response to the twenty-six-point architecture discussion. Their numbering drifted around UI/SDK items, so the record follows the actual statements rather than assuming an empty or misnumbered answer approves a mechanism.

| Topic | User direction | Consequence |
|---|---|---|
| Common manager | One extension/add-on management system with app-specific adapters | Install shared package bytes once; setup, configuration, enablement and permissions remain app-specific |
| Package | Accept explicit package/contribution structure | A package can supply multiple app-specific contributions; exact successor schema remains draft |
| App functions | Expose deliberately designed app functionality through adapters | Plugins can reach only supported functions; preserve existing interfaces through adapters |
| Common operations | Share as much appropriate application functionality as possible between plugins and CLI | Common operation contracts, validation, jobs, results and tooling; app semantics remain owned by each app |
| Permissions | Plugins declare their actions and permissions; each user explicitly allows them | No implicit rights from installation, popularity, official status, project opening or CLI startup; app-specific grants |
| Functional ambition | Design the full level of functionality applications will need from the outset | Cover advanced operations, UI, processing and backend contracts now; this does not approve unrestricted native code or unverified confinement |
| SDK | Straightforward plugin-first SDK with app-specific contributions and permissions | One authoring model, generated routine metadata and app-specific contract libraries |
| Distribution | Official ArtCraft packages take precedence; a new repository records community catalogue/search data | GitHub repositories/releases supply package binaries; Craft does not operate a plugin binary hosting service; repository name/owner still need selection |
| Release format | Use good SDK-generated formats and versioning with GitHub Releases | Download compiled packaged assets, not arbitrary source trees or install scripts |
| Identity | Unique IDs or UUIDs for packages | Preserve source/publisher continuity; UUID choice does not authenticate a publisher; migrate existing dotted IDs explicitly |
| Ranking | GitHub stars take precedence for extension popularity | Official placement first, then meaningful query/compatibility filters and star ranking; stars never grant runtime authority |
| Review | Our people review and approve GitHub PRs before packages enter search/catalogue, official or community | Human catalogue admission; exact per-release review workflow below is a recommended interpretation to prevent unreviewed update substitution |
| Local files | Full local extension installation without catalogue review | Same validation, sandbox, declared capabilities and explicit grants; no mandatory catalogue account or submission |
| Compatibility | Plugin and application compatibility and versioning | Separate package, app contract, runtime, state and project format compatibility |
| Dependencies | Compiled plugins with proper dependency/security practice | Inventory compiled dependencies and licences; no general runtime dependency installer |
| Store | Accept transactional shared store direction | Reuse craft-extensions; concrete new state/layout and retention mechanisms remain draft |
| Enablement and updates | Accept distinct installation/enablement/permission/readiness and safe-update direction | Preserve disabled settings and grants; do not silently widen authority or change saved project processing |
| Project experience | Protect work and expected results with simple UI/UX | Exact release references for live features, useful missing-dependency handling, deliberate migration/baking, safe retention |
| App fixes | Discover and fix app functionality needed by plugins/SDK separately for each app | Record concrete adapter gaps and app-specific verification before implementation; design approval does not start those fixes |
| CLI | Accept shared eligibility, session/job ownership and explicit artifacts | Fresh CLI reuses installed approved eligibility without downloads or new grants |
| Limits | Necessary limits must not be unnecessarily restrictive | Workload-based profiles, observable measured defaults and controlled increases; retain hard protection against unbounded work |
| Themes | Accept data-only themes, explicit activation and app-aware mappings | Preserve app semantics and existing ThemeFile/WidgetPalette separation |
| Resources/workflows | Accept typed resources, readiness and separate workflow execution | No code runs on resource/workflow installation; execution needs a supported contract |
| Recovery | Accept predictable disable/remove/rollback/repair and retained active inputs | Preserve projects/settings; active reader ownership and coherent authority state required |
| Offline and logs | Work offline according to actual functional needs; log reports in the app | Offline-capable features work locally; logs remain bounded and private; remote functions disclose network requirement |
| Licences | Restrict which plugin licences are allowed | Exact catalogue/local/official policy and interaction with proprietary packages remain open; repository dependency/asset rules still apply |
| Verification | Accept real end-to-end and adversarial acceptance before readiness | First-party evidence and community gate evidence are distinct; sg13 stays closed |

## Engineering proposals to make these choices concrete

1. Use one package UUID and stable contribution IDs, with authenticated publisher/source continuity. Maintain dotted aliases for current packages. Neither UUID collision resistance nor GitHub stars proves ownership.
2. Maintain a reviewed metadata repository with approved exact release digests and GitHub repository/release/asset identities. Human approval of each executable release is the default proposal, including official releases. Never follow `latest` directly.
3. Publish authenticated, versioned catalogue metadata using established update tooling. Host only metadata on GitHub; download package binaries from the publisher's GitHub Release assets. No separate binary host or build farm is required by this draft.
4. Reuse app engine operations through explicit descriptors and caller-aware policy. CLI and plugins invoke the same validated behavior but have different authority. A plugin cannot obtain user-level CLI rights through a generic dispatch call.
5. Persist explicit grants per app, package, approved scope and declared authority. Reuse an existing grant only under verified same-authority release continuity. New permissions/scopes require another user decision.
6. Define a complete contribution family catalogue now, including tools/panels/widgets, processing, import/export, jobs and resources. Each app advertises implemented contract versions. Unsupported advanced features are unavailable rather than silently exposed.
7. Use each app's Rust operation registry to generate the authoritative versioned inventory, SDK bindings, CLI discovery/docs and conformance coverage. Preserve working app ABIs initially. WIT may become a generated encoding for a future justified backend; it is not a competing source of truth or a blocker for the SDK.
8. Restrict normal installation to compiled, verified assets without scripts. Dynamic model/data acquisition has separate declared size/digest/licence/readiness policy. Native/GPU/audio execution needs backend-specific proof.

These proposals are not additional user decisions. [The architecture overview](README.md) and companion files develop them for review.
