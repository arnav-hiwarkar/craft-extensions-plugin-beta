# Ordered architecture topics

> **Status (2026-11-10):** history and evidence. The current design is [the Craft plugin architecture](../architecture.md); where this document disagrees with it, the architecture wins.

Status: proposed discussion sequence. The user can reorder it. Eighteen topics split the full system into decisions small enough to examine deeply. The output column names a readable design artifact to refine inside existing docs, not eighteen mandatory new services, crates, PRs or forms.

## Dependencies and depth

T01–T04 establish vocabulary, app ownership and SDK shape. T05–T08 establish authority, compatibility and storage. T09–T11 connect authors to discovery/install. T12–T16 make runtime/project/user behavior complete. T17 addresses operating/product policy and T18 orders delivery. A useful question may expose a dependency early; note it and revisit deliberately rather than forcing a fictional linear design.

For each topic, use one normal example and the relevant adverse scenarios from [coverage](scenarios-and-workflows.md). Show the smallest meaningful data types or function signatures when they settle structure. Explain viable alternatives, concrete consequences and a recommendation. Ask one focused question, wait for the user's response, then continue the topic or record agreement. Do not compress all topic decisions into an options survey.

## Topic completion

A topic is ready to move on when the user understands its role and either agrees on the structure or explicitly leaves a named question open. Record the chosen boundaries, normal/failure/recovery behavior, compatibility effects and evidence still needed. “Discussed” is not “accepted”; a design promise is not runtime proof. The user may return to any topic when later requirements change it.
