# Plugin capability gaps: 3D, materials and textures

Research date 2026-11-18. Read-only survey of TextureCraft, MaterialCraft, SolidCraft and CadCraft
against `craft-extensions` (ext-core/ext-host/ext-kernels/guest), plus web research on the plugin
ecosystems of Substance, Blender, Houdini, Material Maker, MaterialX and asset libraries.
"Observed" means read in source; "estimate" means my reasoning, not a measurement.

## Summary

- **Neither material app can take a plugin today, and the blocker is in the apps, not only the
  adapter.** MaterialCraft's node library is a `static OnceLock<Vec<NodeDef>>` of `&'static str`
  ids and plain `fn(&Ctx)` cook pointers (`materialcraft/crates/nodes/src/catalog.rs:154-168,315`).
  TextureCraft's layer content, mask effects, generators, filters and procedurals are closed Rust
  enums (`texturecraft/crates/core/src/layer.rs:81,204,485,559,925`). Both need an
  "external/plugin" variant that carries an id, a version and opaque parameters, and that
  round-trips unknown data in `.mcraft`/`.tcraft`.
- **Both apps already have what an adapter needs underneath:** a command registry that the CLI,
  RPC and MCP drive by id (≈50 `graph.*`/`file.*` ids in MaterialCraft, ≈80+ `layer.*`, `mask.*`,
  `effect.*`, `bake.*`, `file.*` ids in TextureCraft), snapshot undo (`Session::edit`), a
  content-addressed cook cache (MaterialCraft) and a per-tile dirty compositor (TextureCraft). A
  `materialcraft.session@1` and `texturecraft.session@1` can be generated from those registries
  with little new engine code.
- **The shared platform's compute model does not fit texture work.** Kernels are 2D RGBA-f32 in
  guest memory, `raster.filter@1` is one image in/one out, and a job sandbox caps memory at
  512 MiB (`ext-host/src/wasm.rs:11`). One 4096² RGBA f32 image is 256 MiB, so a 4K node with one
  input and one output already hits the cap. Fuel is metered at 4,000 per pixel
  (`wasm.rs:46`); the audit measured about 17 s per 1080p frame for a Wasm effect (debug build).
  Per-pixel 4K material work must not run in wasmi.
- **Recommendation:** one shared `graph.node@1` contract (typed ports, params, cook), with three
  execution tiers a node can declare: (1) a **host-op graph** (compose built-in nodes and kernels:
  free and fast), (2) a **WGSL function** validated by naga and run by the host on its device with
  loop bounding, dispatch caps and timeouts (the fast path that replaces Material Maker GLSL
  nodes, Designer pixel processors and MaterialX `genglsl` implementations), (3) a **Wasm cook**
  for logic-heavy, low-pixel-count work (FX-map-style scattering lists, analysis, layout), which
  hands pixels to host kernels. Mesh, baking, asset-library and viewport-overlay contracts follow.
- **Native plugins remain needed** only for: closed engines (UVPackmaster-class GPU packers sold
  under an EULA), CUDA/vendor ML inference until a host `ml.*` service exists, Houdini Engine
  bridges, and DCC live links that require a vendor SDK.
- SolidCraft (parametric B-rep CAD on `truck`, wgpu + naga, compute tessellation) and CadCraft
  (AutoCAD-style 2D/3D drafting, DXF/DWG, LISP-style customization planned) are 3D apps but not
  material or texture tools. They are covered briefly at the end of the inventory.

## Shared node contract proposal (`graph.node@1`)

One contract in `craft-extensions`, implemented by a shared host runtime crate (`ext-graph`) that
MaterialCraft, TextureCraft, EffectCraft and PhotoCraft each wire to their own graph or stack. The
app owns the graph, scheduling, caching and UI; the plugin only defines node types.

### Manifest

```toml
[[contribution]]
kind = "node"
id = "hex-tiles"
contract = "graph.node@1.0"
label = "Hex Tiles"
category = "Patterns/Tiles"
domains = ["material", "texture", "effect", "photo"]   # where it may appear
exec = "wgsl"                                          # "graph" | "wgsl" | "wasm"
source = "nodes/hex_tiles.wgsl"
```

### Node definition (returned by `node.describe` or static JSON in the package)

```json
{
  "inputs":  [{"id":"mask","kind":"gray","optional":true}],
  "outputs": [{"id":"height","kind":"gray"},{"id":"id","kind":"color"}],
  "params":  [{"id":"count","kind":"int","default":8,"min":1,"max":64},
              {"id":"bevel","kind":"float","default":0.1,"min":0,"max":1},
              {"id":"seed_offset","kind":"int","default":0}],
  "size":    {"from":"parent"},
  "tileable": true,
  "deterministic": true
}
```

Port kinds v1: `gray`, `color`, `float`, `int`, `vec2..4`, `bool`, `string`; v1.1 adds `mesh`,
`material` (named channel bundle), `points` (instance list). Params reuse MaterialCraft's
`ParamDef` shape (min/max/options/angle/group/curve/gradient), which the host turns into its own
UI; no plugin-drawn parameter panels are needed for 95% of nodes.

### Cook

| Tier | How it runs | Host ops | Use for |
|---|---|---|---|
| `graph` | Package ships a sub-graph of built-in node ids (Designer `.sbs` / Houdini HDA / Geometry Nodes asset model). Host instantiates it | none at cook time | Most "custom nodes" in practice; zero compute risk |
| `wgsl` | Plugin supplies `fn cook(uv: vec2f, p: Params) -> Outputs` plus optional `sample_<input>(uv)` calls; host generates bindings and dispatches a compute pass per output tile | none | Per-pixel generators/filters (Material Maker, MaterialX `genglsl`, UE Custom node equivalents) |
| `wasm` | `craft_node(ctx)` export in a job-like sandbox; receives input **handles**, calls `kernel.*`, `kernel.program`, `image.read_region`, returns output handles | `kernel.*`, `image.*`, `mesh.*` | Scatter lists, analysis, layout, anything branching per element rather than per pixel |

Cache key: `(package digest, node id, params, size, seed, tiling, input keys)` — this slots into
MaterialCraft's existing key (`eval` hashes def id + params + inputs) and TextureCraft's per-layer
dirty tracking. Determinism is required (`seed` is passed in; no clocks, no network in cook).

### Sandboxing WGSL plugins

1. **Never accept a full shader.** The plugin provides function bodies; the host writes the entry
   point, bindings, workgroup size and all resource declarations. Reject `var<storage>`,
   `var<workgroup>`, atomics, barriers, `@group/@binding` attributes and extra entry points in plugin
   source by inspecting the naga IR after parsing.
2. **Validate with naga** (`naga::front::wgsl` → `naga::valid::Validator` with all flags) on install
   and on load, and cache the validated module by digest. Reject on any error; cap source size
   (e.g. 256 KiB), function count, expression count and call depth.
3. **Bound loops.** wgpu/naga gained `force_loop_bounding` (PRs #6929, #7080): loops get an injected
   counter on SPIR-V, MSL and HLSL output; it is disabled only through
   `create_shader_module_trusted`. Plugins must always go through the untrusted path. Dawn has the
   equivalent "loop hardening" transform. Bounded loops alone are not a time limit (2⁶⁴ iterations),
   so also:
4. **Bound work.** Dispatch output in tiles (e.g. 512² per submit), measure each submit with
   timestamp queries, and kill the node (and mark it "too slow" in UI) when a tile exceeds a budget
   (e.g. 250 ms). Driver watchdogs (Windows TDR ~2 s) reset the device on long submits, so small
   submits also keep the app alive. Handle `DeviceLost` by recreating the device and disabling the
   offending node by digest.
5. **Bound memory.** Only host-allocated textures are bound; sizes come from the graph; robust buffer
   access is on in wgpu by default, so out-of-range reads are clamped.
6. **Run off the UI device where possible** (a second `wgpu::Device` or queue for cooks) so a
   plugin can at worst stall cooking, not the viewport.
7. **CPU fallback** for web/WebGL2 and for tests: interpret the same naga IR (or `kernel.program`
   IR) on the CPU; slower but deterministic and portable.

Residual risk: driver compiler bugs reachable through valid WGSL (the reason browsers fuzz naga and
Tint). That is the same exposure every WebGPU page has; treat WGSL nodes as "sandboxed" tier but
keep the kill list and digest revocation.

| wasmtime Cranelift | Optimising JIT; general experience 1.1–2× native (not measured here); SIMD128 maps to NEON/SSE: TF.js measured 1.7–4.5× from SIMD on Wasm, a grayscale benchmark 4.1× | Seconds per node single-threaded, sub-second with threads. Not available on iOS/web-in-browser (browser has its own JIT) |
| wasmtime Winch | Baseline JIT for fast startup; Wasmtime docs: code "will run slower than Cranelift"; TPDE paper places Winch code ~1.14× slower than TPDE, which is 1.64× slower than default Cranelift (≈1.9× slower than Cranelift, derived) | Good for many small plugin modules where compile latency matters |
| Wasm threads | Requires shared memory + `wasi-threads`/host-spawned instances; complicates determinism and fuel | Prefer host-side parallelism (kernels already use 8 threads) |
| Host kernels | Native Rust, rayon, 8 threads (`compute-and-jobs.md`) | Tens of ms per simple op at 4K (estimate from memory bandwidth: 256 MiB read+write) |
| `kernel.program` IR on host | Same as MaterialCraft's function VM, multithreaded | ~0.2–1 s per complex function at 4K (estimate; register VM ~10–50 ns/px/op) |
| WGSL on GPU | Per-pixel generator at 4K is 16.8 M invocations; a mid-range GPU does this in ~1–10 ms for typical noise/pattern code (estimate) | The only path that keeps a 100-node 4K graph interactive |

Recommendations:

1. **WGSL tier first** for per-pixel nodes. It is the fastest, portable through wgpu to
   Vulkan/Metal/DX12/WebGPU, and it is what Material Maker, MaterialX (`genglsl`) and engine
   material functions already use, so ports are mechanical.
2. **Expand host kernels and add `kernel.program`** so Wasm nodes describe work rather than
   perform it. Move MaterialCraft's `nodes/src/ops.rs` primitives and function VM into a shared
   crate used by both kernels and MaterialCraft.
3. **Host-resident image handles** to remove the guest-memory copy and the 512 MiB ceiling.
4. **wasmtime (Cranelift) as an optional desktop backend** for Wasm cooks and importers, with
   epoch interruption instead of fuel for speed; keep wasmi for web and as a fallback. Enable
   SIMD128 in both. Do not invest in Wasm threads.
