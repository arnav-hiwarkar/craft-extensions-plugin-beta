## 1. Executive summary

The security core is solid and was built carefully. It has:
- a signed catalogue with sha256-bound assets;
- per-app declared and live grants checked on every op;
- a wasmi sandbox with fuel, memory caps and deadlines;
- rollback of one transaction per event, with one Undo step;
- a kill list, safe mode, and a shared manager reused by the launcher.

The beta does **not** yet meet the owner's product bar in five ways:

1. **"Essentially any plugin."** The runtime is built for short, synchronous, single-transaction
   events.
   - There are no background jobs, no progress or cancel API, and no persistent storage.
   - There is no network or clipboard op, so `network:<host>` is a permission with no op behind it.
   - Effects are one frame at a time on an interpreter, with no SIMD and no threads.
   - Native plugins cannot contribute effects.
   - Packages cannot be hybrid (Wasm UI plus a native compute helper).
   - There are no prebuilt host compute functions that a filter can call.

   Flagship plugins in the style of Deep Glow, Particular, Twixtor, Neat, Portraiture, Topaz or
   Content Reel are therefore infeasible or impractically slow.
2. **Docking and windows.** EffectCraft and PhotoCraft plugin panels float as `egui::Window`. Only
   FigCraft docks, and only into its own sidebar dock. No app supports real OS windows (viewports),
   and no plugin can change layout.
3. **Manager and store UX.** One shared egui form is used everywhere, with:
   - disk IO and signature verification on the UI thread every frame;
   - free-text "kind" filtering;
   - no categories, tier filter, details page, icons, screenshots, changelog or update-all;
   - one job at a time;
   - hard-coded English strings.

   This is the "clunky" feel.
4. **Catalogue and examples.**
   - The catalogue has one published package, and that package depends on an unpublished one, so
     it cannot be installed.
   - The listing schema has no category, icon or screenshots.
   - Every publish needs a human maintainer to check, merge and sign by hand, and the index must be
     re-signed every 3 weeks.
   - The 15 examples are small demos (18–398 LOC). None replicates a famous AE, PS or Figma plugin.
5. **Robustness gaps.**
   - A single bad plugin disables every PhotoCraft session plugin.
   - Native helper death leaves dead workers with misleading errors.
   - Pauses are per-session only.
   - Several plugin calls block the UI thread for up to 9–10 s.
   - PhotoCraft records no project references.

### Top gaps (ranked)

| # | Gap | Area | Sev |
|---|---|---|---|
| 1 | No background job API (progress, cancel, apply-later). Events are capped at 8–10 s and 2e9 fuel, so heavy compute is impossible. | §6 | blocker |

- The launcher refreshes the catalogue only on first open: minor.

## 3. Effects and filters (per app)

### Current state
- **EffectCraft.**
  - Effects register through `effectcraft_engine::effects::external::register` (`EC/plugins/src/runtime.rs:500-525`).
  - The spec is `gpu: false, float: true` (`EC/effects/src/external.rs:~105`).
  - Each frame passes one premultiplied f32 RGBA buffer plus `time/scale/origin/full/quality` (`EC/plugins/src/effects.rs:82-125`).
  - Parameters are ordinary animatable property groups.
- **PhotoCraft.**
  - Filters are destructive (`PC/engine/src/plugin_filters.rs:381`), using the whole layer as one buffer (`:337-346`).
  - The result is blended by selection coverage (`:359-368`), so the plugin never sees the mask.
  - Masks, channels, Quick Mask, smart objects and non-RGB documents are refused (`:57-71`).
  - Proxy preview runs off the UI thread (`PC/ui-egui/src/canvas/filter_preview.rs:81`).
- **FigCraft.** There is no `raster.filter` contract (`capabilities.md:52`). Image effects on a
  design tool are a big gap compared with Figma plugins that process images.
- **Sandbox limits** (`CE/ext-host/src/wasm.rs:17-30,67-79`; `ext-host/Cargo.toml:17`):
  - wasmi interpreter, features `deterministic`, `portable-dispatch`;
  - no SIMD, no threads;
  - 512 MiB transform memory, 4000 fuel per pixel.

  This caps a PC layer at about 30 MP (16 B/px plus a copy), and EC halftone takes about 17 s per
  1080p frame (`effectcraft/docs/plugin-testing.md:156`).

### Missing or shallow
- No temporal or neighbour-frame input. The public EC v0.24.1 had ABI 2 neighbour frames, so this
  is a regression (`continuation-2026-11-17.md`, "Evidence carried forward").
- No region, ROI or tiling requests; no multiple inputs (layer parameters such as a matte or
  displacement map); no GPU path; no per-instance opaque state (B9-FEATURE-STATE).
- No native effects (`CE/ext-core/src/manifest.rs:248-249`).
- PC has no smart filters or adjustment-layer plugins, no mask or channel targets and no non-RGB
  modes. FC has no image filters at all.
- Renders get no pause or failure count. A trapping effect retries every frame (`EC/plugins/src/effects.rs:180-184`).

### Severity
- Blocker for the "what AE/PS plugins do" requirement: glow, blur, distort, keying and denoise all
  need neighbours, regions, multi-input or speed.

### Fix direction (smallest coherent)
1. **Speed.** Change the execution engine: either a JIT (wasmtime with fuel or epoch interruption,
   still deterministic enough), or wasmi with `simd` plus host-side row-parallel tiling. Keep ABI 1
   and add a `craft_filter_tile` export so the host can parallelise across tiles.
2. **`raster.filter@1.1`.** Add declared ROI expansion (padding), additional named inputs
   (layer-parameter references) and an optional neighbour-frame request list. Bound the counts and
   bytes.
3. **Persistence (later).** PC non-destructive smart-filter instances (reusing the EC parameter
   model), and an FC image-fill filter slot.

## 4. Panels, windows, docking, layout

### Current state
- **EffectCraft.** Surfaces are drawn as `egui::Window` (`CE/ext-ui/src/plugin_ui/mod.rs:190`) from
  `EC/ui-egui/src/plugins_ui.rs:108-127`, outside the craft-ui `Workspace` (`EC/ui-egui/src/lib.rs:55`).
  - The contract slot says "(beta: a floating panel)", while the manifest doc says "dockable panel"
    (`CE/ext-core/src/manifest.rs:36`).
- **PhotoCraft.** The same floating windows (`PC/ui-egui/src/plugins_ui.rs:71`). No plugin code
  appears in `dock.rs` or `panels/panel_docking.rs`.
  - Titles are forced to "<title> · <plugin-id>" (`PC/plugins/src/runtime.rs:350`).
- **FigCraft.** A per-sidebar plugin dock with tabs, side and width persisted in prefs
  (`FC/ui-egui/src/plugin_dock.rs:1-28,285`). Windows are `egui::Window`
  (`FC/ui-egui/src/plugins_ui.rs:160-164`).
- **Everywhere.**
  - No OS windows: `show_viewport` is used only for canvas tabs and the screen picker in PC.
  - No position, size or modal options.
  - No `ui.window.close`, no panel open/close/visibility events (`STATUS.md` "Open items").
  - Plugins cannot open their own panels.
  - `component` nodes always fall back (`ui.md:139-149`).
- **Window limits differ by app:** 4 per plugin (EC/FC) versus 32 per app (PC)
  (`capabilities.md:39`).

### Missing
- The owner requires "docked panels in every app, hosted in-app windows and real OS windows". Two of
  the three apps lack docking, and all three lack OS windows.
- Layout-change requests are missing: "open my panel next to Layers", workspaces and presets.
- Talking to windows is missing: window close events, focus, and messaging between a plugin's
  surfaces is implicit (same session), but there are no lifecycle callbacks.

### Severity
- Blocker for EC and PC docking. Major for OS windows and lifecycle.

### Fix direction
1. Add a `PluginPanel(key)` tab kind to each app's `Workspace<String>`. Draw it with the existing
   `PluginUi::draw_json` (not `window()`). Persist placement in the workspace layout, and keep the
   floating `window()` path for `ui.window.open`. This is backlog UI-DOCK, already scoped in
   `community-comparison-and-backlog.md`.
2. Add a `surface` option `{kind: "window" | "os-window", size?, min_size?}`. Render `os-window`
   through `ctx.show_viewport_deferred` in the shared renderer, so all apps gain it together. Unify
   the limit (for example 4 per plugin, plus a per-app cap) in `ext-core::ui`.
3. Add events `surface.opened`, `surface.closed` and `surface.visible`. Add ops `ui.panel.show`
   (user-visible request, rate-limited) and `ui.window.close`. Add advisory layout hints
   (`dock: "right" | "bottom", near: "<builtin panel id>"`) that the host may ignore. Plugins never
   get to rearrange core panels: a hint applies only to the plugin's own surface on its first open.

## 5. Native plugins and helper protocol safety

### Current state
- **Protocol** (`CE/ext-host/src/native.rs:1-36`):
  - JSON lines, at most 1 MiB per line, 64-line bounded queue for backpressure;
  - 10 s start, 60 s per-event cap;
  - `env_clear` and a private working directory (`:88-93`);
  - its own process group, killed with `/bin/kill -KILL -pgid` (`:39-52`);
  - re-checks consent, kill list and enablement on each call;
  - supervised every 100–500 ms (`:152-170`).
- **Consent** is per version (STATUS "Fixed in this phase").
- Native packages are **session-only**. `module` is ignored (`manifest.rs:78`), and effects are
  refused (`:248`).
- **Platforms:** the example ships linux-x86_64 and macos-aarch64 helpers
  (`examples/native-system-stamp/craft-plugin.toml:12`).

### Missing or shallow
- **No OS confinement.**
  - There is no macOS seatbelt (`sandbox-exec`) profile and no Windows AppContainer or Job Object.
  - On Windows `kill_group` is a no-op (`native.rs:51-52`).
  - A helper can escape its group on purpose (STATUS "Open items").
  - The owner asked for "as safe as practical". A default-deny file and network profile with an
    opt-out is practical on macOS and Linux (landlock, seccomp, or bwrap if present).
- **Downloaded helper binaries:**
  - no code-signing or notarization check, and no handling of the Gatekeeper quarantine xattr (no
    grep hits for `quarantine` or `codesign`);
  - macOS will likely block an unsigned helper extracted by the app, or it will run unsigned.
    Behaviour is unverified.
- **No pixel or bulk transport.** Pixels go through JSON at 1 MiB per line, so a native denoiser or
  AI upscaler cannot be fed. There is no shared-memory or file-handle transport.
- **No progress or job messages** in protocol 1. The host-side event wait (8–10 s in the apps) is
  shorter than the helper's 60 s cap (`PC/plugins/src/runtime.rs:97,247` vs `native.rs:33`).
- **Helper death is invisible to the user.**
  - `supervise()` false ends the worker loop (`EC/plugins/src/runtime.rs:1015-1018`;
    `PC/plugins/src/runtime.rs:161-164`; `FC/plugins/src/runtime.rs:162`).
  - Later dispatches report "worker busy" (PC `:251`) or "worker stopped" (FC).
  - There is no restart with backoff and no Problems entry.
- **Missing platform binary.** In PC, a missing helper for the current platform fails the whole
  `Runtime::load` (`PC/plugins/src/runtime.rs:~134` `ok_or(...)?`), which kills all PC session
  plugins (see §13).
- **Stale doc comment.** `native.rs:13-15` says "permissions are moot", but the apps still call
  `authorize` (`capabilities.md:233-237`).

### Severity
- Major: confinement, transport, death handling. Minor: the stale comment.

### Fix direction
1. Add `Helper::exit_status()`. On death, mark the contribution "stopped: helper exited (code)" in
   Problems, and restart lazily on the next event with up to 3 restarts and exponential backoff,
   counted toward the pause.
2. **Protocol 1.1.**
   - Add `progress {id, value, label}` and `cancel {id}` records.
   - Add `job` start/finish records (tying into §6).
   - Add a `blob` transfer via a host-created temp file or anonymous shared-memory file descriptor,
     announced by handle. The host decides which pixels to send (PC `pixels.get` semantics).
3. **Confinement.**
   - macOS: launch the helper under a generated seatbelt profile (deny network unless a
     `network:*` grant, deny writes outside the work directory).
   - Linux: landlock where available.
   - Windows: Job Object with kill-on-close.
   - Label the result "Native (confined)" versus "Native (full access)" in consent, so many native
     plugins need less trust.
4. **Install time.** Strip or verify the quarantine xattr policy deliberately. Optionally verify a
   detached author signature (minisign) recorded in the release record.

## 6. Long-running and heavy compute: jobs, progress, cancel

### Current state
- **Session events** are synchronous transactions:
  - 8 s per event, 5 s per transaction, 10 s per op round trip (`EC/plugins/src/runtime.rs:37-43`);
  - `FUEL_PER_EVENT = 2e9` (`CE/ext-host/src/wasm.rs:30`).
- **PC filters** run via `jobs::run` with progress and cancel infrastructure
  (`PC/engine/src/jobs.rs:1-25,156-175`). The plugin cannot report progress; cancel is polled
  between 20M-fuel slices (`wasm.rs:27,361-394`).
- **Manager install jobs** show a spinner and a cancel that only discards the result
  (`CE/ext-ui/src/lib.rs:31-72`).
- A `progress` UI node exists (`ui.md` Display), but no plugin code can run long enough to use it.

### Missing
- The whole JOBS backlog item:
  - start or acknowledge within the deadline;
  - run without holding a document transaction;
  - report progress and honour cancel;
  - apply in a new owner transaction after revalidating version, grants, document epoch and target
    ids.
- No host job tray or status-bar entry for plugin jobs, and no job concurrency limits.

### Severity
- Blocker for "long-running heavy compute jobs" and "big feature plugins".

### Fix direction
1. Add host ops `job.start {label, cancellable}` → `job_id`, `job.progress {job_id, value, label}`
   and `job.finish {job_id, result}`.
2. Add a new guest export `craft_job(ptr, len)`. It runs on a worker with its own fuel budget
   (slices; cancel and grant checks between slices) and only **read** ops against a captured
   snapshot (or picked inputs).
3. On finish the host delivers a `job.done` event, which runs as a normal short transaction and can
   apply results with existing ops. Stale results are rejected by an epoch check (the backlog's
   design).
4. Native helpers get the same through the protocol 1.1 progress and job records.
5. UI: one shared `JobsPanel` in `craft_ext_ui` (list, progress, cancel) that each app adds to its
   status bar.

## 7. Built functions and own native helpers

### Current state
- Session plugins can invoke canonical app operations:
  - EC: `effect.apply/remove/reorder` (`EC/plugins/src/contract.rs:66-188`);
  - PC: the `filter.apply` allowlist (`PC/engine/src/session_filters.rs:15-73`) and
    `adjustment.apply`;
  - FC: boolean, flatten and outline ops.
- Filters have no `call` import at all (`CE/guest/src/host.rs:1-4`; import whitelist at
  `wasm.rs:97`).
- A package is either Wasm or native. It cannot be a Wasm UI plus its own native helper
  (`manifest.rs:78,135-137`).

### Missing
- **"Built functions".** Plugins cannot call prebuilt Rust kernels on buffers they hold, for
  example: gaussian/box blur, resample, convolution, FFT, colour conversion, distance transform,
  optical flow, path tessellation, text shaping. These would let a sandboxed effect be fast without
  native code, which is the cheapest path to flagship-class effects.
- **Hybrid packages.** Wasm UI and logic with an optional consented native compute helper
  (UXP-hybrid style). Today a plugin wanting one native kernel must make its whole UI native
  full-access.
- **No calls between plugins** (deferral).

### Severity
- Major.

### Fix direction
1. Add a versioned `craft.kernels@1` contract. It is a set of pure, host-side, bounded functions
   operating on guest memory ranges, with no document access, so it needs no permission and is safe
   in filters. Expose it as a fifth import (`craft.kernel`) with op name plus pointer and length,
   charged to fuel by work size.
2. **Hybrid manifests.** Allow `module` plus `[native.helper]` together. The Wasm side calls
   `helper.request {…}`, which is gated by native consent and reaches the helper through a jobs
   channel (§6). Consent text names exactly what the helper is for.

## 8. Guest SDK surface versus flagship needs (`CE/guest`)

### Current state (about 1.6k LOC)
- `filter!` and `session!` macros (`guest/src/lib.rs:118-170`).
- `FilterCtx` getters `f/int/b/choice/text/color/point` plus `seed` (`guest/src/filter.rs:12-61`).
- `Image::get/set/offset` (`:70-92`).
- `Event` enum with `Init, Command, Ui, Tool, App, Dispose, Unknown` (`guest/src/session.rs:12-52`).
- `call(op: &str, args: Value) -> Result<Value, CallError>` (`guest/src/host.rs:116`).
- Form `describe`/`update` for dynamic parameters (`guest/src/form.rs`).
- UI tree builders (`guest/src/ui.rs`, 509 LOC).
- `log`.

### Missing for flagship plugins
- **Typing.** Typed op bindings (`ec::layer::new_solid(..)`, a typed `PcLayer`). Every op is a
  string plus `json!`. Typed schemas exist only for the UI family (`CE/ext-host/src/schema.rs`;
  backlog TYPED-CONTRACTS).
- **Storage, network, clipboard.** No storage API (permission docs call private storage "free" at
  `permission.rs:10`, but no op exists). No network or clipboard wrappers (no ops exist).
- **Jobs.** No progress, cancel or job API (§6).
- **Image helpers.** No region or tile iteration, no multi-input images, no neighbour frames, no
  colour-space helpers, no SIMD-friendly views, no kernels (§7).
- **Async UI.** Every UI interaction is a full round trip and a tree replace. There are no
  incremental patches outside FC forms (STATUS "Open items").
- **Testing.** No mock host or `craft_guest::testing` to unit-test sessions off-app;
  `craft-ext test` covers effects only (`cli-reference.md:91-100`).
- **Language.** Rust only. No TypeScript or AssemblyScript bindings (UXP and Figma authors are
  JS-first).

### Severity
- Major.

### Fix direction
1. Generate typed Rust modules per contract from `OpSpec` once the args/results schemas are
   structured (extend `ext-host/src/schema.rs` beyond the UI family). Start with the ops the
   flagship examples use.
2. Add `storage::{get,set}` (per plugin, per app, quota-bounded; backlog SETTINGS) and `job::*`.
3. Ship `craft_guest::testing::MockHost`, which records ops, replays canned replies and asserts on
   trees.
4. A JS path later (compile to Wasm via an embedded QuickJS module) once typed schemas exist.

## 9. Plugin Manager UI (`CE/ext-ui/src/lib.rs`, 740 LOC): why it feels clunky

### Structure
- Tabs Browse, Installed, Updates, Problems, plus "Refresh catalogue" (`:311-319`).
- Setup consent and the project prompt are `egui::Modal` (`:110`, `:637`).
- A single `Jobs` slot runs one background job (`:31-72`).

### Problems (each verified in source)
1. **Per-frame IO and crypto on the UI thread.**
   - `browse()` builds a new `Manager` and calls `search()` every frame (`:410-411`). This reads
     the cached index and verifies its signature (`ext-store/src/manager.rs:85-87`).
   - `browse_row` re-reads `Catalogue::cached` once **per row, per frame** (`:~437-441`).
   - `installed()` reads `store.state()` and each manifest per frame (`:479,494`). The Updates tab
     does the same (`:331-338`).
   - This will stutter with real catalogue sizes.
2. **Synchronous writes on click.** Enable, disable, revoke, pin, remove and native toggle
   (`:546-587`) and setup confirm (`:179-214`) all write synchronously. The cross-process store lock
   can stall the frame.
3. **Weak search and filtering.**
   - Two free-text boxes: "Search plugins" and "Filter kind (for example effect, panel, command)"
     (`:403-406`).
   - No category, tier, app or native facets as chips.
   - Tags are searchable (`ext-core/src/catalogue.rs:295`) but never displayed.
   - No sorting (rank only), no pagination, no virtualised list.
   - No ScrollArea in the view itself; the host must wrap it.
4. **Install is a multi-step chore.** Users must click "Find compatible releases", then pick a
   version from a combo, then "Install X", then "Confirm install", then the Setup modal
   (`:~450-477`, `:297-310`). The newest compatible version is not offered by default with one
   click.
5. **No details page.** No icon, screenshots, long description, changelog, permissions preview
   before install, author page or homepage. The Updates tab says "Review the author's release notes
   in the source repository" (`:363`).
6. **Updates.** One button per plugin, and no update-all. Browse rows have no "installed" or
   "update available" badge. In the launcher you must pick an app before checking (`:327-350`).
7. **Single-job queue.** A second `start` is silently ignored (`:40-42`). Cancel waits for the
   download (`:66`). There is no byte progress.
8. **Strings.** Raw English with no i18n hooks (`tl!` is used elsewhere in the launcher). A
   debug-looking "Plugin UI engine: Framework (Egui fallback)" dropdown is shown to users in EC
   (`EC/ui-egui/src/plugins_ui.rs:156-163`).
9. **Visual design.** `ui.group` stacks of labels using default egui widgets and no app theme
   components. The trust badge is a text line (`helpers.rs:18`).
10. **Crash isolation is reactive only.** A pause shows with a Resume button, but there is no
    persisted "disabled after crash" state, no crash count and no "report" from the problem row
    (report exists only on Installed, `:589`).

### Severity
- Major. This is the owner's "professional" bar.

### Fix direction (one coherent rewrite of the view layer, same `Manager` API)
1. **`ManagerModel` cache.** Load index, state and manifests once on a background thread. Refresh
   on store-generation change or on job completion. The view reads only memory.
2. **Writes.** All writes go through `Jobs` with a multi-job queue, or through a tiny write worker.
   Use optimistic UI with error toasts.
3. **Layout.**
   - Left rail: All, Installed, Updates (n), Problems (n), and Categories (from §11).
   - Top: search with facet chips (Tier, App, Kind, Native, Free of network).
   - Body: virtualised cards with icon, name, vendor, tier badge, one-line summary and a primary
     button (Install / Open / Update / Enabled toggle).
   - Detail pane: screenshots, description, changelog, permissions per app, version history and
     rollback, report link.
4. **One-click install.** Install the newest compatible release, then open the consent sheet with
   recommended defaults.
5. **Polish.** Add update-all, i18n keys, and remove the engine dropdown from user surfaces.

## 11. Catalogue schema, tiers, categories, search, distribution, review burden

### Current state
- **`PackageSummary`** (`CE/ext-core/src/catalogue.rs:48-70`): id, name, summary, vendor, repo,
  stars, tags, kinds, apps, native, license, latest, updated, file hash and size, stars_date.
- **Tier** lives on the vendor (`catalogue.rs:37-46`; `tier.rs`). Badges read "Official",
  "✔ Verified vendor", "Community", "Not reviewed (local file)" and "Development".
- **Search** ranks by exact, prefix, tag/word, then summary/id, then tier and stars
  (`catalogue.rs:277-302`).
- **Release records** contain the asset URL in the author's GitHub release, sha256 and size, plus
  an embedded manifest (`CP/plugins/io.github.arnav-hiwarkar.film-looks/releases/1.1.0.toml`).
  Upstream lesson: release assets must come from the package's repository
  (`check_asset_url`, `upstream-integration-2026-11-17.md`).
- **Signing:** one online ed25519 key, a 30-day expiry and serial rollback protection
  (`catalogue.rs:1-30`). TUF is deferred.
- **Process:** "No bot and no CI" (`CP/MAINTAINERS.md:3`). A maintainer runs `catalogue check`,
  does a quick manual review, merges, builds, signs locally and commits `dist/`
  (`MAINTAINERS.md:15-21`). The index must be re-signed every ≤ 3 weeks (`:21`).

### Missing or defects
- **Schema gaps.**
  - No package-level `category`; categories live per contribution in the manifest and are not
    surfaced.
  - No `icon`, `screenshots`, `description_md`, `homepage`, `changelog`/release notes,
    `min_app_version` display or `platforms` (native) in the summary.
- **No category taxonomy** shared across apps (Effects ▸ Blur/Distort/Stylize/Color…, Tools,
  Panels, Automation, Import/Export, AI).
- **Defect.** `film-looks` 1.1.0 requires `io.github.arnav-hiwarkar.halftone ^1.0`
  (`releases/1.1.0.toml:22-23`), but halftone is only in `examples/pending`. The only published
  package therefore cannot resolve its dependency. It also has `commit = "000…"` and `repo_id = 0`
  (`listing.toml:4`).
- **Review burden.** The owner wants it minimal, and today every listing and release needs a human
  merge plus a local signing step.
  - A GitHub Action can run `catalogue check` on PRs (asset fetch, hash, manifest match, licence,
    permission diff).
  - Community-tier updates from an already-listed vendor whose permissions did not widen can then
    be auto-merged.
  - Only signing needs the key: an offline step, or a protected-environment CI job if the owner
    accepts that risk.
- **Missing community signals.** No reviews, ratings, install counts or "featured" curation. These
  were explicitly deferred (no accounts), but a maintainer-curated `featured.toml` needs no
  accounts.

### Severity
- Major: schema, process, defect. Minor: TUF (already deferred).

### Fix direction
1. **Schema 1.1** (additive, `#[serde(default)]`):
   - `category` (an enum from a shared taxonomy) and `icon` (an https URL in the author repo, or an
     embedded small PNG hash-bound in the package file);
   - `screenshots[]` (hash-bound URLs), `description` (markdown, size-capped), `homepage`;
   - per-release `notes`; `platforms`.

   Have `catalogue build` copy these from `listing.toml`.
2. **Automation.** Add `catalogue check` as a PR workflow in craft-plugins, a PR template, and
   auto-labels (new-vendor, native, permission-widening). Humans review only labelled PRs.
3. **Fix the published data.** Publish halftone, or drop the `requires` from film-looks, and fill
   in the real commit and `repo_id`.

## 12. Per-app grants and consent

### Current state
- Grants are keyed per app and plugin in store state (`state.apps[app][id].grants`;
  `CE/ext-ui/src/lib.rs:84-100`).
- Every op checks declared plus granted permissions on the document thread
  (`CE/ext-host/src/api.rs:221-233`). Live views:
  - EC `StoreGrants` every 250 ms (`EC/plugins/src/grants.rs:30-63`);
  - PC and FC re-read per check;
  - all fail closed.
- Filters re-check between fuel slices and at commit (`PC/plugins/src/lib.rs:166-201`).
- Install never enables; setup is per app with the author's "why" text; native consent is per
  version (STATUS).

### Missing or shallow
- **No just-in-time prompt.** A missing grant returns `-2` and the plugin must explain it. Figma and
  UXP surface a host prompt instead.
- **Scope is coarse in FC.** `node.get/update/delete` need full-document access because selection
  scope is deferred (`FC/plugins/src/contract.rs:47,57`).
- **No "grant to all apps" convenience** in the launcher Setup. Each app is set up separately via
  the app chooser.
- **Permissions without ops.** `network:<host>`, `clipboard.*` and `files.*` (EC/FC) can be declared
  and granted, but nothing uses them (`capabilities.md:198-203`). The consent UI shows rights that
  do nothing.

### Severity
- Minor/major. The design is sound, and the restrictiveness comes from missing ops, not from the
  grant model.

### Fix direction
1. Add `permission.request {permission, reason}`, which shows a host sheet (rate-limited, only
   during a user-initiated event).
2. Implement selection scope in FC.
3. Hide or ban declaring permissions that the target app provides no op for (`craft-ext check`
   warning).
4. Add an "apply same choices to other apps" checkbox in the launcher setup.

## 14. Crash and panic isolation

### Current state
- **Wasm.**
  - Traps, budget, memory and invalid output never panic the host; the instance is discarded and
    re-instantiated (`CE/ext-host/src/wasm.rs:1-9,560-578`).
  - After 3 failures the plugin is paused for the session, with a Resume button
    (`EC/ui-egui/src/plugins_ui.rs:136-149`; `PC/plugins/src/runtime.rs:70,171-196`;
    `FC/plugins/src/runtime.rs:179,364`).
- **UI trees.** Validated with node and depth caps (`CE/ext-core/src/ui/tree.rs:41-67`;
  `egui_engine.rs:23`). A bad tree shows "could not be drawn" or "not drawn yet".
- **Safe mode.** EC has `--safe-mode` plus an env var. PC and FC have an env var only
  (`PC/plugins/src/lib.rs:10-12`; `FC/plugins/src/lib.rs:156`).
- **Lints.** The apps deny `clippy::panic`, `unwrap` and `todo` in plugin crates
  (`PC/plugins/src/lib.rs:3`; `FC/plugins/src/lib.rs:145`; `CE/ext-ui/src/lib.rs:2`).

### Missing or defects
- **PhotoCraft all-or-nothing load (major).**
  - `Runtime::load` uses `?` on each plugin's module read, `Plugin::load` and native platform
    lookup (`PC/plugins/src/runtime.rs:~121-134`).
  - The caller does `Runtime::load().ok()` (`PC/engine/src/plugin_sessions.rs:61`).
  - So one corrupt `.wasm`, or a native package with no helper for this OS, silently removes every
    plugin's panels, tools and commands. The fix is to load per plugin and collect errors into
    Problems, as EC and FC do.
- **No `catch_unwind`** anywhere in CE or the app plugin crates (grep: 0 hits).
  - Lints reduce the risk, but a panic in adapter op code (on the document/UI thread), in the egui
    renderer drawing plugin trees, or in a dependency (serde, image decode) would take down the app.
  - Wrap `PluginUi::draw_json` and adapter `call` dispatch in `catch_unwind(AssertUnwindSafe)`,
    converting a panic into a plugin failure and pause.
- **UI thread blocking.**
  - PC: widget events run `session.execute("plugin.uiEvent")` and block up to 10 s
    (`PC/ui-egui/src/plugins_ui.rs:87`; `plugin_sessions.rs:103-125`). Tool begin, update and commit
    run synchronously in `canvas_pointer` (`plugins_ui.rs:214-238`).
  - FC: `deliver(wait=true)` polls up to 9 s for commands, init on every document switch, and
    resume (`FC/plugins/src/runtime.rs:185,429-430,479`).
  - A slow plugin therefore freezes the app ("must not crash the app" includes hangs). Delivery
    should be asynchronous, with results applied on the next frame, and only transactions on the
    owner thread.
- **Pause and quarantine are session-only.** A plugin that crashes on start crashes again every
  launch (it is paused only after 3 failures each time). Persist "auto-disabled after N crashes;
  re-enable?" in store state per app.
- **Effects in renders** have no failure counter (§3).
- **Safe mode is undiscoverable in PC and FC.** There is no launch flag, no "start without
  plugins" prompt after a crash, and no indicator. Add an after-crash prompt using a sentinel file
  written at startup and cleared at clean exit.
- **No watchdog for runaway host work** triggered by plugins, such as huge `layer.tree` replies.
  Replies are capped at 8 MiB per instance and 64 MiB per app (`wasm.rs:21-25`), which is OK.

### Severity
- Major: PC all-or-nothing load, UI-thread blocking, no `catch_unwind`. Minor: persistence of
  pauses, safe-mode UX.

### Fix direction
- Covered in each item above.

## 17. "Never overhaul or break core app functionality"

### Current state
- **Good.** There are no layout ops, no undo/history/settings/management ops (`capabilities.md:204`),

- **Good.** Each event is one Undo step. EC and PC refuse outside edits during a plugin gesture

- **Good.** Plugins cannot re-register core commands; plugin command ids are namespaced
  `plugin.<id>.<contribution>`.

### Risks
- **Freezes** (§14 UI-thread blocking) are the main "break core" risk today.
- **PC per-frame store polling plus 100 ms repaints** while any plugin is loaded
  (`PC/ui-egui/src/plugins_ui.rs:94`; `plugin_sessions.rs:54`) cost idle CPU and battery.
- **Panel canvases** can request costly polygon drawing every frame with no per-revision cache
  (STATUS).

### Severity
- Major (freezes). Minor (idle cost).

## 18. Recommended sequencing (smallest coherent path to the owner's bar)

1. **Robustness hotfixes** (small, high value):
   - PC per-plugin load;
   - async event delivery in PC and FC;
   - `catch_unwind` at the renderer and adapter seams;
   - helper-death reporting and restart;
   - persistent crash auto-disable;
   - after-crash safe-mode prompt.

3. **UI-DOCK in EC and PC.** OS-window surfaces. Surface lifecycle events.
4. **JOBS contract** (Wasm plus native protocol 1.1), with progress and cancel, and a shared jobs

5. **Compute.** A faster engine plus tiling, the `craft.kernels@1` contract, and hybrid packages.
6. **State.** Project data and private settings ops; FC `plugin_data`; EC per-instance state.
7. **SDK and DX.** Typed bindings generated from schemas, a mock host, `dev --watch`, a console, and

8. **Flagships.** Build them as each contract lands, and use them as acceptance tests.
