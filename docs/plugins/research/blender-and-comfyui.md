# How Blender and ComfyUI handle plugins

Status: research note, 2026-11-10. Gathered from the official documentation and security write-ups listed under Sources. Facts not found in those pages are marked "not documented". Compared with [the Craft plugin architecture](../architecture.md) at the end.

## Blender extensions

| Area | How it works |
|---|---|
| Package | A `.zip` with `blender_manifest.toml`, plus `__init__.py` for an add-on or `theme.xml` for a theme. Built and validated with `blender --command extension build` and `validate` |
| Manifest | Required: `schema_version`, `id`, `version` (semver), `name`, `tagline`, `maintainer`, `type` (`add-on` or `theme`), `blender_version_min` (at least 4.2), `license` (SPDX list). Optional: `blender_version_max`, `platforms` (`windows-x64`, `windows-arm64`, `macos-x64`, `macos-arm64`, `linux-x64`), `wheels`, `permissions`, `tags`, `website`, `copyright`, `[build]` include and exclude paths |
| Code | Python running inside Blender. **No sandbox**; Blender's own docs say Python "does not restrict what a script can do" |
| Permissions | `files`, `network`, `clipboard`, `camera`, `microphone`, each with a one-sentence reason of at most 64 characters (`network = "Need to sync motion-capture data to server"`). **Declarative only:** nothing enforces them. Add-ons must check `bpy.app.online_access` (the "Allow Online Access" preference, overridable with `--offline-mode`), but the docs say "Blender cannot prevent third-party add-ons from violating this rule" |
| Storage | Add-ons must not write into their own folder (it can be read-only and is deleted on upgrade); they use `bpy.utils.extension_path_user()`, kept across upgrades and removed on uninstall |
| Dependencies | Self-contained: unmodified PyPI wheels inside the package (one per platform for binary wheels), or vendored pure Python. `--split-platforms` builds one zip per platform. No runtime downloads |
| Repositories | Default: one remote repository (extensions.blender.org) plus two local ones. Users can **add any remote repository by URL**, with an optional access token. Self-hosting: a static `index.json` generated by `blender --command extension server-generate`, a dynamic server, or a fork of the whole platform. "System" repositories are read-only, for studios bundling extensions with Blender |
| Install and update | Search and install in Preferences ▸ Get Extensions, drag in a URL, or Install from Disk (no updates for disk installs). Updates are **manual**: Refresh Remote, then Install Available Updates. A per-repository "check on startup" shows a status-bar notice. Disable to stop temporarily; remove is permanent |
| Store review | Upload at extensions.blender.org with a Blender ID. The extension waits in a **public Approval Queue where anyone can comment**; only moderators approve. Reviewers test in Blender, check manifest, images and listing, and review code: `open()` calls, writes only to the user extension path, network calls gated on `online_access`, no auto-updaters, dependencies as wheels. A linter runs. Reviews usually take a couple of days, but backlogs of about 150 have been reported |
| Store rules | Add-ons must be **GPL-3.0-or-later**; bundled images and fonts CC0. No "Blender" in names and no implied endorsement. No obfuscated code or bytecode. No remote code loading, external downloads or dependence on other extensions. No ads, donation buttons, paywalls or registration gates in the UI (funding links allowed in the listing). Network use must be declared, respect the preference, need no extra login, and send no data without consent |
| Not documented | Malware scanning, code signing, takedown or reporting process |

## ComfyUI custom nodes

| Area | How it works |
|---|---|
| Code | A Python package in `ComfyUI/custom_nodes/` with `__init__.py` exporting `NODE_CLASS_MAPPINGS`. A node is a class with `CATEGORY`, `INPUT_TYPES` (required, optional, hidden inputs), `RETURN_TYPES` and `FUNCTION`; a newer V3 schema uses `io.ComfyNode` with `define_schema`. Optional browser UI: `WEB_DIRECTORY` of JavaScript files registered with `app.registerExtension`, loaded into the web page |
| Loading | At startup ComfyUI imports every module in `custom_nodes`. A failed import is reported in the console; changes need a restart. Node names must be unique across the installation |
| Sandbox and permissions | **None.** Nodes run in the server process with full access. Snyk: "any Python file within `./custom_nodes` will get executed"; ComfyUI has no built-in authentication. A sandboxed ComfyUI and "permission management" appear only as roadmap and open questions (Jan 2025) |
| Comfy Registry | registry.comfy.org: publisher accounts (permanent IDs, often the GitHub username), node IDs that are globally unique, semver versions that are **immutable once published**, deprecation without removal. `pyproject.toml` `[project]` (name, version, license, description, dependencies, Repository URL) and `[tool.comfy]` (`PublisherId`, `DisplayName`, `Icon`, `Banner`, `requires-comfyui`, `includes`). Published with `comfy node publish` or a GitHub Action that runs when the version changes |
| Registry rules | No `eval`/`exec`, no runtime `pip install` through subprocesses, no obfuscation. Nodes are scanned (AI and static analysis; the scanner is private) and passing nodes get a verification flag; the registry can "quickly ban nodes" |
| ComfyUI-Manager | The main browser and installer. Installs from the Registry or legacy `custom-node-list.json` channels (1-day cached, local, or remote lists), runs each pack's `requirements.txt` (pip) and `install.py` on install, fetches and applies updates, disables and enables packs, saves **snapshots** of the whole installation and restores them, and offers **"Install Missing Custom Nodes"** for a loaded workflow. Workflow JSON records the node pack and version |
| Manager security | `security_level` = `strong`, `normal`, `normal-` or `weak` gates *management actions* (installing outside the default channel, downloading non-safetensors models, updates), not what nodes do at runtime. Git-URL installs and pip installs need separate flags (`allow_git_url_install`, `allow_pip_install`, both off by default and only for loopback listeners) |
| Incidents | Malicious or vulnerable nodes (ultralytics crypto miner, ComfyUI_LLMVISION, 2024); Manager pip-field injection (CVE-2024-21574); upload path traversal into `custom_nodes` (CVE-2024-21575); unsafe `eval` in nodes (CVE-2024-21576, -21577); a Doyensec advisory of remote code execution through custom-node install in Manager before v3.31 (PDF not readable here). Response: the January 2025 rules above, scanning, a public security review channel, and a planned remote kill switch for malicious nodes |

## Compared with the Craft design

| Topic | Blender | ComfyUI | Craft |
|---|---|---|---|
| Sandbox | None | None | **WebAssembly sandbox**; native only with a full-access label |
| Permissions | Declared with reasons, not enforced | None | Declared, granted per app, **enforced on every call** |
| Network switch | Global "Allow Online Access", honour system | None | Network permission per domain, made by the host; optional machine policy "no network" |
| Manifest | TOML, platforms, version range, wheels | `pyproject.toml` with `[tool.comfy]` | `Craft.toml` plus a generated manifest; contracts instead of app versions |
| Dependencies | Bundled wheels; no extension-to-extension dependency | pip at install time (the main attack path) | Compiled in; data-package dependencies only; nothing runs at install |
| Distribution | Platform hosts files; any remote repo can be added | Registry hosts versions; channels and git URLs | Author GitHub Releases, pinned digests, one signed catalogue, local files |
| Review | Public approval queue, moderator approval, code review | Automated scanning plus verification flag | Bot checks; human look for first listing, wider permissions, new owner; two maintainers for native |
| Immutability | Not stated | Published versions immutable | Digest pinned per release |
| Updates | Manual check; "update all" | Fetch, then update | Always ask; 48-hour hold on bot-merged updates |
| Licence | GPL-3.0-or-later | Any | MIT and/or Apache-2.0 in the store |
| Project needs plugins | Not covered | "Install Missing Custom Nodes"; versions in workflow JSON | Project plugin list, "This project uses 3 plugins: Install all" |
| Rollback | Not covered | Installation snapshots | Choose any listed version; setup export and import |
| Kill switch | Not documented | Planned | Revocation by digest, version or publisher |
| Storage | `extension_path_user()` | Not covered | Private storage per package per app |

**What the comparison suggests:**
1. **ComfyUI shows what happens without a sandbox.** It had install-time code execution through pip, malicious nodes and eval injections, and its response came afterwards: scanning, bans, a planned kill switch, a planned sandbox. The Craft design has all of these from the start. ComfyUI's `install.py` and pip-at-install path is the one to never copy.
2. **Blender shows that declared permissions without enforcement are disclosure, not protection.** It still has a good habit worth copying: a **reason per permission** (we have it as `why`) and a **global online switch** (we have it as machine policy).
3. **Ideas not yet in the Craft design:**
   - **Extra catalogue sources:** a studio's or community's own repository, as Blender allows with any remote URL and a token.
   - **A public approval queue** where anyone can comment before a moderator approves.
   - **Installation snapshots** with one-click restore, as ComfyUI-Manager has.
   - **Read-only "system" installs** for studios that deploy a fixed plugin set with the app.
